# 재고 자동 발주 HITL 에이전트 — 설계 스펙

- 작성일: 2026-09-28
- 과제: 모두의연구소 10강 「사람이 승인하는 에이전트 만들기 [프로젝트]」
- 상태: 사용자 검토 대기

## 0. 목적과 성공 기준

### 무엇을 만드는가
실제 온라인 소매점 판매 기록을 보고 LLM이 상품별 **다음 주 발주량**을 정한다. **위험한 발주만** 거래처로 발주서를 보내기 직전에 멈추고, 사람(팀장)의 결재를 받은 뒤 이어서 실행한다. 나머지는 자동으로 발송한다. 이 과정을 **아이소메트릭 사무실** 화면으로 보여 준다.

### 요건 대조 (교재 5강 + 퀘스트 공지)

| 퀘스트 평가기준 | 이 스펙에서 충족하는 곳 |
|---|---|
| 1. 바꿀 수 없는 결정 전에 멈추고, 사람의 답으로 이어서 실행 | §2.2 `review`(interrupt) → `Command(resume)` → `send_po` |
| 2. 승인이 필요 없는 건은 자동 처리, 대기 건 보관 | §2.2 자동 경로, §5 영속 체크포인터(SQLite/Postgres) |
| 3. 승인 기준 설계와 이유 설명 | §3 사전 등록 채점, 기준 후보와 막는 위험 |
| 4. 승인 과정을 확인하는 웹 데모 | §4 사무실 + 결재 화면 + 발송 기록 + 기준 검증 탭 |
| 5. REPORT.md 정리 | §7 |
| (공지) 모듈에서 배운 워크플로 패턴 활용 | §2.3 패턴 대응표 |
| (공지) LLM 답변의 확률성 | §3.4 반복 측정, 기준 C5 |
| (교재) 환불 주제 제외 | 주제: 재고 발주 |

### 범위 밖
실제 거래처 연동(발주서 발송은 목), 수요 예측 모델의 정밀도 개선, 로그인/권한, 다국어.

## 1. 데이터와 정답 라벨

### 1.1 원천
- **UCI Online Retail II** (https://archive.ics.uci.edu/static/public/502/online+retail+ii.zip, 약 45MB, 로그인 불필요)
- 영국 온라인 선물 도매·소매점, 2009-12-01 ~ 2011-12-09, 1,067,371행
- 원본은 `data/raw/`에 스크립트로 내려받고 커밋하지 않는다. 가공 결과(주간 JSON)만 커밋한다.

### 1.2 전처리 (`data/prepare.py`)
- 제외: 수량 ≤ 0, 단가 ≤ 0, 취소 송장(`C`로 시작), 상품 코드가 `^\d{5}[A-Z]?$`가 아닌 행(우편료·수수료 등)
- 주 단위(월요일 시작, `W-SUN`)로 상품별 판매 수량을 합산한다. 단가는 상품별 중앙값을 쓴다.
- **"오늘" 주 t**의 후보: t 직전 8주 중 6주 이상 판매가 있는 상품. 이 가운데 **고정 시드(42)로 200건**을 뽑는다.
- 건마다 저장하는 값: 상품 코드, 상품명(영문), 단가(£), 8주 판매 배열, 8주 평균·표준편차·변동계수, 지난주 판매.
- **정답**(t주의 실제 판매량)은 별도 파일 `data/weeks/<t>.answers.json`에 저장하고 `eval/`에서만 읽는다.

### 1.3 사용하는 주 (고정)
| 용도 | 주 시작일 |
|---|---|
| 개발(기준 선택) | 2011-06-06 |
| 검증(보고) | 2011-09-05, 2011-10-03 |

### 1.4 사전 실측 (설계 근거, 2026-09-28 측정)
- 활성 상품: 주당 1,219~1,543개
- 주간 판매 변동계수 중앙값 0.84~0.88, 상위 10% 1.42~1.46
- 단순 예측(8주 평균)이 50% 넘게 빗나간 비율 59%. 빗나간 금액이 £50를 넘는 비율 33~39%
- 다음 주 판매가 8주 평균의 2배를 넘은 비율 14~21%
- 발주액(8주 평균 × 단가) 중앙값 약 £50, 90분위 £244~297, 99분위 £790~857

### 1.5 정답 라벨 (사전 등록, 변경 금지)
- **손해액** = |AI 원판단 발주량 − 실제 t주 판매량| × 단가(£)
- **`should_stop` = 손해액 > £100**
- 근거: 발주액 중앙값의 약 2배이고, 원화로 약 18만 원이다. 담당자가 한 건을 30초 동안 검토하는 비용보다 확실히 크다.
- 알려진 한계: 과잉 재고 비용과 결품 손실을 같은 무게로 본다. REPORT의 한계 항목에 기재한다.
- 환율: 화면 표시용 고정값 **£1 = ₩1,800**

## 2. 에이전트 구조

### 2.1 배치 그래프 — 이번 주 판단 (`agent/batch_graph.py`)

```
START → prepare_week ──Send×200──▶ judge_item ──▶ collect → END
```

- `prepare_week`: 주간 JSON을 읽어 200건을 준비한다.
- `judge_item`: 건마다 LLM을 호출한다. `Send`로 병렬 fan-out하고, 동시 호출 수 상한은 8로 둔다.
  - 입력: 상품명, 단가, 8주 판매, 통계. **t주 실제 판매는 넣지 않는다.**
  - 출력(JSON 스키마, Structured Outputs):
    ```json
    {"qty": 정수 ≥ 0, "reason_ko": "한두 문장", "demand_signal": "평소|증가|급증|감소", "name_ko": "상품명 한국어"}
    ```
- `collect`: 판단 결과를 `runs/<t>/judgments.json`에 캐시하고, 건마다 발주 건 그래프 스레드를 시작한다.
- 반복 판단 옵션 `--samples N`(기본 1). N > 1이면 모든 샘플을 저장하고, 대표값은 **첫 번째 샘플**로 한다. 흔들림은 C5와 §3.4에서만 사용한다.

### 2.2 발주 건 그래프 — 한 건의 승인 절차 (`agent/order_graph.py`)

- thread_id 형식: `<세션>:<주>:<상품코드>`

```
START → check_rules ─(통과)─────────────────────────────────▶ send_po → END
            └(걸림)→ enqueue → review ⏸ ─ approve ────────────▶ send_po
                                  ├─ edit(qty) ───────────────▶ send_po
                                  ├─ reject(reason) ──────────▶ record_reject → END
                                  └─ redo(instruction) ─▶ rejudge ─▶ check_rules
```

| 노드 | 역할 | 부수효과 |
|---|---|---|
| `check_rules` | §3.2에서 선택된 기준 적용 → `flags` | 없음 |
| `enqueue` | 결재함 투입 이벤트 발행(SSE) | 이벤트만 |
| `review` | **`interrupt`만 한다.** 승인 화면 페이로드(§4.2 다섯 칸)를 담는다 | **없음** (재실행 함정 방지) |
| `send_po` | 목 발주서를 팩스 로그에 기록 | **thread_id 키로 멱등** |
| `record_reject` | 반려 사유 저장 | 로그 |
| `rejudge` | 담당자 지시를 붙여 LLM 재판단, `redo_count += 1` | LLM 호출 |

- `redo_count ≥ 2`이면 `review` 페이로드에서 redo 선택지를 뺀다. 서버도 redo 요청을 400으로 거부한다.
- 재판정 뒤에도 `check_rules`를 다시 지난다. 이번에 기준을 통과하면 자동 발송한다.
- `decision.edit_qty`는 0 이상의 정수여야 하고, 8주 평균의 10배를 넘을 수 없다.

### 2.3 워크플로 패턴 대응 (REPORT에 수록)

| 패턴 | 적용 위치 |
|---|---|
| 병렬화 (fan-out/fan-in) | 배치 그래프 `Send` → `judge_item` → `collect` |
| 라우팅 | `check_rules` 뒤 조건부 분기, `review` 뒤 응답별 분기 |
| 평가자-최적화 루프 | `redo` → `rejudge` → `check_rules` (최대 2회) |
| Human-in-the-Loop | `interrupt` + `Command(resume)` + 영속 체크포인터 |

### 2.4 State (`OrderState`)

| 키 | 내용 |
|---|---|
| `item` | code, name_en, price_gbp, hist8[], mean8, std8, cv8, last_week |
| `judgment` | qty, reason_ko, demand_signal, name_ko, samples[](옵션) |
| `flags` | [{rule, 설명, 측정값, 기준값}] |
| `decision` | {action: approve/edit/reject/redo, edit_qty?, reason?, instruction?} |
| `redo_count` | int |
| `po` | {qty, amount_gbp, amount_krw, sent_at, by: auto/human, thread_id} |
| `status` | auto_sent / pending / approved / edited / rejected / failed_to_human |

- 대기 건 판별: `get_state(thread).next == ('review',)`

## 3. 승인 기준과 사전 등록 채점

### 3.1 기준 후보

| 기호 | 조건 | 막으려는 위험 |
|---|---|---|
| C1(X) | 발주액 `qty × price` > £X, X ∈ {100, 200, 300} | 한 번에 큰돈이 나가는 발주 |
| C2 | `qty > 2 × mean8` | LLM이 수요를 과장해 재고를 떠안는 경우 |
| C3 | `cv8 > 1.2` | 원래 예측이 어려운 상품이라 판단을 믿기 어려운 경우 |
| C4 | `demand_signal ∈ {급증, 감소}` | LLM 스스로 평소와 다르다고 판단한 경우 |
| C5 (옵션) | 3회 샘플의 `(max − min) / median > 0.3` (median이 0이면 max > 0일 때 참) | 같은 질문에 답이 흔들리는 확률적 불안정 |
| 안전장치 (항상 켬) | LLM 실패 / 스키마 위반 | "모르면 사람에게". 비교표에서는 별도 행으로 센다 |

### 3.2 비교할 조합
기준 없음 · C1(100) · C1(200) · C1(300) · C1(200)+C2 · C1(200)+C2+C3 · C1(200)+C2+C4 · C1(200)+C2+C4+C5 · 전부 멈춤

### 3.3 세는 값 (`eval/metrics.py`)
- 개입률 = 멈춘 건 / 200
- 놓침 = `should_stop`인데 멈추지 않은 건수, **놓친 손해 합계(£)**
- 헛멈춤 = `should_stop`이 아닌데 멈춘 건수, 멈춘 건 중 헛멈춤 비율
- 참고: LLM 발주 총손해 vs 단순 예측(round(mean8)) 발주 총손해

### 3.4 선택 규칙 (사전 등록, 변경 금지)
1. **개발 주**에서 개입률 ≤ 25%인 조합만 남긴다.
2. 그중 **놓친 손해 합계가 가장 작은 조합**을 고른다. 동률이면 헛멈춤이 적은 것.
3. 고른 조합을 **검증 주 2개**에 그대로 적용해 보고한다. 검증 결과를 보고 다시 고르지 않는다.
4. 개발 주는 LLM 판단을 **3회 반복**(`--samples 3`)한다. 각 샘플을 대표값으로 삼았을 때의 표를 3개 만들어 **지표의 흔들림 폭(최소~최대)**을 보고한다. 선택은 샘플 1 기준으로 한다.
5. 조건 1을 만족하는 조합이 없으면 그 사실을 보고하고, 개입률이 가장 낮은 조합을 고른다.

> **보정 (2026-09-28, 결과를 본 뒤 · 사용자 승인):** 과제 요건 "계산 가능한 기준 2가지 이상"을 위 규칙에 빠뜨렸다.
> 사전 등록 규칙으로는 C1(£200) 하나가 뽑혔다. 같은 규칙을 **내용 기준이 2개 이상인 조합**(ALL 제외)에만 다시 적용해
> C1(£200)+C2 를 고른다. 개발 주에서 두 조합의 놓친 손해는 £3,672 로 같고 헛멈춤이 1건 늘었다.
> 원래 결과는 `runs/eval.json` 의 `preregistered` 에 남긴다. 라벨·상한·검증 주는 바꾸지 않았다.

### 3.5 비용 (실행 전 동의 필수)
- 호출: 개발 주 200×3 + 검증 주 200×2 = 약 1,000회 (C5 포함 시 검증 주도 ×3 → 약 1,800회)
- OpenAI 소형 모델. 모델명과 단가는 실행 직전 공식 가격으로 확정한다. 추정 약 $1 안팎.
- 캐시(`runs/`)가 있으면 다시 호출하지 않는다. `insufficient_quota` 오류가 나면 즉시 중단하고 이어서 돌릴 수 있게 한다.
- 실행 후 실제 호출 수와 토큰 사용량을 보고한다.

## 4. 웹 데모

### 4.1 사무실 장면 (`web/`, 의존성 0, Canvas)
- Deep-research-agent의 아이소메트릭 엔진(`iso.js`, `renderer.js`, `actors.js`)과 Kenney CC0 에셋(characters/furniture/floor/library)을 재사용한다. `CREDITS.md`를 함께 옮긴다.
- 배치: 입고함 → 수요 분석가 책상 3개 → 검사관 → (팩스기 | 팀장 결재함) + 캐비닛
- 서류 한 장 = 발주 건 하나. 자동 통과 건은 팩스로, 걸린 건은 결재함으로 간다. 캐비닛에 "보관 중 N건"을 표시한다.
- 재생 속도: 1× / 4× / 건너뛰기
- 현황판: 전체 · 자동 발송 · 대기 · 승인 · 수정 승인 · 반려 · 판단 실패

### 4.2 결재 화면 (모달)
| 칸 | 내용 |
|---|---|
| ① 원문 | 상품명 영문 + 한국어, 상품 코드 |
| ② 핵심 정보 | 발주량, 발주액 £/₩, 8주 판매 막대그래프, 8주 평균 |
| ③ AI 판단과 근거 | reason_ko, demand_signal |
| ④ 멈춘 이유 | 걸린 기준마다 "측정값 > 기준값" |
| ⑤ 통과시키면 | "거래처에 N개, £X(₩Y) 발주서가 팩스로 발송됩니다" |
- 응답: 승인 · 수량 수정 후 승인 · 반려(사유 필수) · 다시 판정(지시 입력, 남은 횟수 표시)
- **실제 다음 주 판매는 이 화면에 표시하지 않는다.**
- 72시간 넘게 대기한 건은 "기한 초과 · 상위 결재자에게 넘김" 배지를 단다. 자동 승인은 하지 않는다.

### 4.3 탭
- 🏢 사무실 (결재함 목록 포함)
- 📠 발송 기록: 자동/사람 승인 구분, 수정 전후 수량
- 📊 기준 검증: §3 비교표(개발/검증), 흔들림 폭, LLM vs 단순 예측, 선택된 기준과 이유

### 4.4 서버 API (`server/`, FastAPI)
| 메서드 | 경로 | 용도 |
|---|---|---|
| POST | `/api/session` | 방문자 세션 생성(캐시 판단으로 결재함 시드) |
| POST | `/api/run?week=` | 주 처리 시작(캐시 재생 또는 BYOK 라이브) |
| GET | `/api/events` | SSE (서류 이동·상태 변화) |
| GET | `/api/pending` | 대기 목록(`next == ('review',)`) |
| GET | `/api/orders/{id}` | 결재 화면 페이로드 |
| POST | `/api/orders/{id}/decision` | 응답 → `Command(resume)` (대기가 아니면 409) |
| GET | `/api/faxlog`, `/api/eval` | 발송 기록, 기준 검증 데이터 |
| POST | `/api/reset` | 세션 초기화 |

- BYOK: `X-OpenAI-Key` 헤더로만 받는다. 저장하거나 로그에 남기지 않는다. 키가 없으면 캐시만 재생하고 redo를 비활성화한다.

## 5. 영속성과 배포

- 체크포인터: 로컬 `SqliteSaver`(`state/checkpoints.sqlite`), 배포 `PostgresSaver`(`DATABASE_URL`). 환경 변수로 전환한다.
- 배포: Render 무료 웹 서비스(FastAPI가 API와 정적 파일을 함께 제공) + Neon 무료 Postgres
- 세션 분리: thread_id 접두사 = 세션 ID. 24시간 지난 세션의 스레드와 로그를 정리한다.
- 시크릿: `.env`(gitignore), Render 환경 변수. 커밋 전에 시크릿 패턴을 검사한다.

## 6. 오류 처리

| 상황 | 대처 |
|---|---|
| LLM 호출 실패 / 스키마 위반 | 1회 재시도 → 실패 시 `status=failed_to_human`, 결재함으로 보낸다 (자동 발송 금지) |
| 비상식적 qty (음수, 평균의 10배 초과) | 스키마·검증 단계에서 결재함으로 보낸다 |
| 중복 클릭 / 동시 결재 | 대기 상태 확인 후 resume, 아니면 409. `send_po`는 멱등 |
| 서버 재시작 | 체크포인터에서 대기 건을 복원한다 |
| `insufficient_quota` | 즉시 중단, 완료분 캐시 유지 |
